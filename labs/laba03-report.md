Мета роботи: Ознайомитися з методами безпечної модифікації даних у базі даних PostgreSQL, навчитися виконувати транзакції, використовувати механізми COMMIT, ROLLBACK і SAVEPOINT, працювати із зовнішніми ключами та каскадними операціями. Опанувати створення тригерів, журналювання змін, версіонування даних, збережених функцій і процедур, а також резервне копіювання та перевірку прав доступу.

Використане програмне забезпечення

Supabase — хмарна платформа для роботи з базами даних PostgreSQL.

SQL Editor — середовище для виконання SQL-запитів.

PostgreSQL — система керування реляційними базами даних.

Створення структури бази даних

Для виконання лабораторної роботи було використано хмарну платформу Supabase, яка підтримує систему керування базами даних PostgreSQL.

У межах схеми library_lab3 було створено та підготовлено базу даних для роботи бібліотеки.

Було використано такі основні таблиці:

authors — зберігає інформацію про авторів книг: ім'я, прізвище, повне ім'я та країну.

books — містить інформацію про книги: назву, рік видання, автора, ISBN та кількість примірників.

readers — зберігає дані читачів: ПІБ, електронну пошту, номер телефону та дату реєстрації.

lendings — містить інформацію про видачу книг читачам, дати видачі та повернення, а також статус видачі.

Для забезпечення цілісності даних використовувалися первинні та зовнішні ключі, обмеження унікальності та перевірки допустимих значень.

Результат: створено структуру бази даних бібліотеки, яка дозволяє зберігати інформацію про авторів, книги, читачів та видачу літератури.

Робота з транзакціями та ROLLBACK

Для забезпечення безпечної модифікації даних було використано транзакції PostgreSQL.

Спочатку виконано транзакцію для зменшення кількості доступних примірників книг після їх видачі читачам. Для цього використовувалися команди BEGIN, UPDATE та COMMIT.

Команда BEGIN розпочинає транзакцію, UPDATE змінює дані, а COMMIT підтверджує та зберігає виконані зміни.

Також було перевірено роботу команди ROLLBACK. Для цього тимчасово змінено країну автора з ідентифікатором 1 на тестове значення. Після виконання ROLLBACK зміни було скасовано.

Під час повторного перегляду таблиці authors було підтверджено, що початкове значення країни автора залишилося незмінним.

Результат: перевірено механізми підтвердження та скасування транзакцій. Дані можна змінювати без ризику збереження небажаних змін.

Використання SAVEPOINT

Для перевірки механізму часткового скасування транзакцій було використано команду SAVEPOINT.

У межах однієї транзакції було виконано дві операції оновлення кількості доступних примірників книг.

Після першої операції створено контрольну точку my_savepoint. Друга операція збільшувала кількість примірників іншої книги на 5.

За допомогою команди ROLLBACK TO SAVEPOINT другу зміну було скасовано, тоді як перша залишилася чинною після виконання COMMIT.

Під час перевірки результатів було встановлено, що для книги №4 кількість доступних примірників збільшилася з 1 до 2, а для книги №5 залишилася незмінною — 1.

Результат: перевірено можливість часткового скасування змін у транзакції за допомогою SAVEPOINT без скасування всіх попередніх операцій.

7. Журнал аудиту та тригери

Для автоматичного відстеження змін у базі даних було створено таблицю audit_log, яка зберігає інформацію про виконані операції.

Таблиця містить назву зміненої таблиці, тип операції, ідентифікатор запису, попередні та нові значення даних, дату й час зміни та користувача, який виконав операцію.

Для автоматичного запису інформації було створено функцію log_book_changes() та тригер books_audit_trigger.

Тригер спрацьовує після додавання, оновлення або видалення записів у таблиці books та передає відповідну інформацію до журналу аудиту.

Під час перевірки було змінено назву книги «Кобзар» на тестове значення. Після цього в таблиці audit_log з'явився запис із попередніми та новими даними. Надалі початкову назву книги було відновлено.

Результат: реалізовано автоматичне журналювання операцій додавання, зміни та видалення книг за допомогою тригера.

Версіонування даних та історія змін книг

Для збереження попередніх станів записів було створено таблицю book_versions. Вона зберігає інформацію про книгу до внесення змін.

Було створено функцію save_book_version() та тригер book_version_trigger, який автоматично зберігає попередню версію книги перед її оновленням.

Контрольні запитання

1. У чому полягає різниця між операторами INSERT, UPDATE та DELETE? Які обмеження необхідно враховувати при їх використанні?

INSERT використовується для додавання нових записів у таблицю, UPDATE — для зміни вже існуючих записів, а DELETE — для видалення записів.

Під час їх використання необхідно враховувати обмеження цілісності: первинні та зовнішні ключі, унікальність значень, заборону NULL і перевірку допустимих значень через CHECK.

2. Чому використання умови WHERE є критично важливим в операціях UPDATE та DELETE? Які наслідки можуть бути від її пропуску?

Умова WHERE визначає, які саме записи потрібно змінити або видалити. Якщо її пропустити, команда UPDATE змінить усі записи таблиці, а DELETE видалить усі записи. Це може призвести до втрати або неправильного оновлення даних.

3. Що таке транзакція та які властивості ACID вона забезпечує? Поясніть кожну властивість на конкретному прикладі.

Транзакція — це група операцій із базою даних, які виконуються як одна логічна дія. Вона забезпечує чотири властивості ACID:

Atomicity (атомарність) — усі операції виконуються повністю або скасовуються.

Consistency (узгодженість) — після транзакції дані залишаються коректними та відповідають обмеженням.

Isolation (ізольованість) — паралельні транзакції не повинні неправильно впливати одна на одну.

Durability (довговічність) — після підтвердження транзакції зміни зберігаються.

Наприклад, під час видачі книги читачу потрібно одночасно додати запис про видачу та зменшити кількість доступних примірників.

4. Яка різниця між командами COMMIT та ROLLBACK? У яких ситуаціях використовується кожна з них?

COMMIT підтверджує всі зміни, виконані в транзакції, та зберігає їх у базі даних.

ROLLBACK скасовує зміни поточної транзакції.

COMMIT використовується, коли всі операції виконані правильно, а ROLLBACK — коли виникла помилка або потрібно скасувати зміни.

5. Що таке точки збереження SAVEPOINT і як вони дозволяють керувати транзакціями більш гнучко порівняно з простим ROLLBACK?

SAVEPOINT — це точка збереження всередині транзакції, до якої можна повернутися за допомогою ROLLBACK TO SAVEPOINT.

На відміну від звичайного ROLLBACK, який скасовує всю транзакцію, точка збереження дозволяє скасувати лише частину виконаних операцій, залишивши попередні зміни.

6. Які типи обмежень цілісності ви знаєте? Як кожен з них допомагає підтримувати коректність даних у базі?

Основні типи обмежень цілісності:

PRIMARY KEY — унікально ідентифікує кожен запис.

FOREIGN KEY — забезпечує зв'язок між таблицями.

UNIQUE — забороняє повторення значень.

NOT NULL — забороняє залишати обов'язкове поле порожнім.

CHECK — перевіряє відповідність значень заданим умовам.

Ці обмеження допомагають уникати помилок і підтримувати правильність даних.

7. Що таке каскадні операції та які варіанти їх поведінки існують при видаленні або оновленні батьківських записів?

Каскадні операції — це автоматичні дії над пов'язаними записами під час зміни або видалення батьківського запису.

Основні варіанти:

CASCADE — автоматично видаляє або оновлює пов'язані записи.

SET NULL — встановлює NULL у зовнішньому ключі.

SET DEFAULT — встановлює значення за замовчуванням.

RESTRICT — забороняє видалення або зміну, якщо існують залежні записи.

NO ACTION — не виконує автоматичної дії та перевіряє обмеження цілісності.

8. Яку роль відіграють тригери в забезпеченні цілісності даних та автоматизації операцій? Наведіть приклади їх практичного застосування.

Тригери — це спеціальні механізми, які автоматично запускають певні дії у відповідь на операції INSERT, UPDATE або DELETE.

Вони використовуються для ведення журналу аудиту, збереження історії змін, перевірки даних та автоматичного оновлення пов'язаних записів.

У лабораторній роботі тригер використовувався для автоматичного запису змін книг до таблиці audit_log.

9. Чому необхідно використовувати блокування записів при паралельному доступі? Які проблеми можуть виникнути без них?

Блокування записів потрібне для захисту даних під час одночасної роботи кількох користувачів або транзакцій.

Без блокування можуть виникати конфлікти змін, втрата оновлень та неправильні результати операцій. У PostgreSQL для цього можна використовувати команду SELECT ... FOR UPDATE.

10. Як рівні ізоляції транзакцій впливають на можливі аномалії при паралельному виконанні операцій? Який рівень слід обирати для різних сценаріїв?

Рівні ізоляції визначають, наскільки транзакції захищені від впливу інших одночасних операцій.

Основні рівні:

READ UNCOMMITTED — допускає читання незавершених змін інших транзакцій. У PostgreSQL працює як READ COMMITTED.

READ COMMITTED — дозволяє читати лише підтверджені зміни.

REPEATABLE READ — гарантує стабільність повторного читання даних у межах транзакції.

SERIALIZABLE — забезпечує найвищий рівень ізоляції, наближуючи паралельне виконання до послідовного.

Для звичайних операцій часто достатньо READ COMMITTED, а для складних операцій, де особливо важлива узгодженість даних, можна використовувати SERIALIZABLE.

Висновок

Під час виконання лабораторної роботи №3 було закріплено практичні навички роботи з базами даних PostgreSQL у середовищі Supabase. Було створено та заповнено таблиці бібліотеки, виконано додавання, оновлення й видалення записів. На практиці перевірено роботу транзакцій, команд COMMIT, ROLLBACK і SAVEPOINT, зовнішніх ключів та каскадного видалення. Також було реалізовано журнал аудиту, тригери для автоматичного збереження змін, механізм версіонування даних, функції та процедуру. Додатково створено резервну копію таблиці, перевірено права доступу й використано блокування рядків.

У результаті роботи отримано практичний досвід безпечного керування даними, контролю змін і підтримки цілісності бази даних.
